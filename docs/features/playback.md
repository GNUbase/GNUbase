# Transport and playback

The transport, and how audio, MIDI and instrument tracks play. The processing graph they run in is in [architecture.md](../architecture.md).

- The **transport** (`Transport` in `src/engine/audio`) holds the project cursor, the left and right locators and the playback modes. Commands (`transport.play`, `stop`, `toggle`, `record`, `locate`, `set`, `exchangeLocators`, `get`) send requests through a lock-free queue; the audio thread applies them at the start of its next block, or the command thread right away while no device runs. For every block it hands the graph a `graph::TransportBlock`: whether it plays and records and, while playing, segments of consecutive project positions. In cycle mode a new segment starts at the exact sample where playback reaches the right locator and jumps to the left one, so loop points are sample-accurate for any block size; with the right locator before the left one the range is skipped instead. In arranger mode the active arranger chain decides where playback goes instead of the cycle ([arranger.md](arranger.md)). Processors read the block from `ProcessContext::transport`; the built-in `positionProbe` outputs each frame's position, so tests check where every frame played. Start from cycle start and return to start position on stop are settings; the selection-based start modes belong to the UI, which knows the selection. `transport.toggle` with a `setting` switches cycle, punch in and out, the metronome or recording, and `transport.locate` with `by` moves the cursor by seconds, as the transport bar's buttons and keys do ([transport-bar.md](transport-bar.md)); the metronome is only a switch until the click comes (#101). Every transport command emits `transport.changed`. `transport.record` from stop counts in first when the count-in is on, and playback starts at the exact sample where it ends ([metronome.md](metronome.md)).
- **Punch in and out, pre-roll and post-roll** (#102, reference manual pp. 318-319, 336-338) are transport settings (`transport.set`). The punch points are the locators. With `punchIn`, playback that reaches the left locator starts recording there, at the exact sample, also on every cycle lap; with `punchOut`, recording that reaches the right locator ends there and playback goes on. With the user setting `audio.stopAfterPunchOut` (the reference's Stop after Automatic Punch Out preference, off by default; the engine hands it to the transport) playback stops after an automatic punch out, `postRollAmount` samples later if `postRoll` is on, unless it cycles; it stops at the first block that starts at or after that point, and the cursor goes there (or back to the start with `returnToStart`). Recording again during the post-roll doesn't stop. With `preRoll`, playback starts `preRollAmount` samples before the cursor (not before the project start), and `transport.record` from stop starts recording at the cursor, or at the left locator with `punchIn` if that comes later. If a cycle would jump back before playback gets there, recording starts where the pre-roll starts, or with `punchIn` at whichever comes later, that or the left locator. A locate while recording waits for its start, during the pre-roll or for the punch in, moves the start by the same rule: recording starts where the locate goes, or with `punchIn` not before the left locator. The amounts go up to an hour at 768 kHz, and positions (the cursor, `transport.locate`, `audition.scrub` and the locators) up to `g_maxPosition`, 2^48 samples: the commands refuse more, and the transport clamps whatever reaches it, such as the end of a project with an event past it, so nothing on the audio thread overflows; `transport.locate` `by` stops there as it stops at 0. In a cycle that skips the range the record start lies in, recording starts at the left locator, where playback lands, and recording started by hand during the pre-roll cancels the waiting start. Built-in processors behind the plugin wrapper see which segments record too. `returnToStart` returns to the cursor. `transport.record` answers with what the audio thread will do, so `recording` is false while it waits for the record start. Each segment of the transport block says whether it records, so punches split segments like cycle jumps; `PlayedPositions` keeps it per frame for the recorder, and plugins get it as `plugin::Transport::Recording`.
- **Changes the audio thread makes on its own**, punching in and out and stopping after a punch out, reach the command thread through `Transport::sync`: once the audio thread has applied every request, it takes over whether the audio thread plays and records. The cue thread sees `Transport::changes` move and posts `transport.update`, which syncs and announces `transport.changed`; `audio.render` syncs when it's done.
- **Audio tracks** play their audio events from disk streams (`Playback` and `TrackPlayer` in `src/engine/audio/playback.h`). When the graph is rebuilt, each audio track gets a **playlist**: its events in the project's samples, sorted and cut where they overlap. Where events overlap the one added last (the highest id) is in front; muted events don't play and hide nothing. The playlist has **layers**: layer 0 holds what is in front, the layers behind it the parts of hidden events that still sound during a crossfade or an auto crossfade. A hidden event plays behind only where transitions active there join it to the event in front: where that is its partner in a transition, or is joined to its partner by further transitions, as when a third event takes the front during a crossfade. Along the way it takes the fades behind the front of each link, so what plays behind an event fades out and in with it; once they have faded it out, it stays silent until the event in front changes or a fade brings it in again from silence. An event placed over a crossfaded join hides both events as far as its own transitions reach. A track plays at most a few events at once. The audio thread renders each layer into a buffer of its own and adds the layers up front first, so a sum of several events is bit for bit the same for every block size. Each entry carries its **gain ramps** (fades, clip fades, crossfade halves) in the project's samples, built with the playlist, and the audio thread multiplies its samples by them sample by sample, without allocating; the curves are in `src/engine/audio/fades.h`. Mirrored ramps over the same range add up to exactly 1, so a crossfade between two halves of the same audio passes it through unchanged. A clip at another sample rate is converted by its disk stream, and its offset and length are scaled to the project's rate. A clip's channels go one to one to the track's channels, a mono clip goes to all of them, extra clip channels are left out; a mono track reaches a stereo bus through the graph's mono-to-stereo mix.
- Each audio track has 16 **voices**: disk streams of its clips. The command thread positions them ahead of playback ("cueing") at every point where playback enters an entry: the cursor, the start of each next entry whose clip doesn't simply continue the one before, and the left locator after a cycle jump. The audio thread takes the voice that is waiting at the frame it needs, so events and cycle jumps start at their exact sample; within an entry it reads on from the same voice. A voice that isn't there in time, or a late disk stream, leaves silence, counted as `playbackDropouts` in `audio.get`. Cue and audio thread hand voices over by compare-and-swap on each voice's state: a cue repositions a voice only if the audio thread hasn't started reading it since the cue looked, and the audio thread skips a voice that a cue is repositioning.
- Offline rendering (`audio.render`) cues and then waits until every voice's buffer is full before each block, so it never drops out and renders the same samples every time. In real time a cue thread cues the next two seconds every 5 ms; `transport.play` and `transport.locate` cue the start position first and wait up to two seconds for it. Real time and offline rendering produce the same samples as long as the disks keep up.
- **MIDI and instrument tracks** play their parts through a `MidiSequencer` per channel (`src/engine/audio/sequencer.h`), the channel's processor. It reads the channel's notes and controllers from an immutable sequence that the command thread publishes after every change, and turns the transport's segments into events at their sample offset: at one sample note-offs first, then controller events, then note-ons, so a note that ends where the next one starts is retriggered cleanly. It keeps every sounding note with its end and sends its note-off even if the note was edited or removed meanwhile. A stop, a locate and a cycle jump end all sounding notes at their exact sample. See below for chasing. An instrument channel (`InstrumentChannel`) runs its sequencer, adds the events of the MIDI channels routed to it and feeds them to its instrument. Each source's events keep their order, so a note of no length from live input or a plugin arrives as sent; between sources, note-offs come first at one sample, then the other events, then note-ons. When the MIDI channels fill an instrument's input in one block (1024 events), a note-off takes the place of the latest other event, so no note hangs. Sequencers and instruments are kept per channel across rebuilds, so editing never cuts a sound; when a MIDI track is routed elsewhere, the instrument releases the notes it still holds. SysEx events point into the sequence, which stays alive until the next block.
- **Chase** (#105): where playback starts or jumps (a locate, a cycle jump), each sequencer sends what is in effect there, so instruments sound as they would have if playback had run up to that position. Right after the jump's note-offs come the controller events: the last control change of each channel and number, the last program change and the last pitch bend of each channel before the position, in time order (at one position control changes first, so a bank select precedes its program change). A kind with an event at the position itself, on any of the tracks chased, isn't chased: that event plays there. Then the controller events at the position, then the notes that sound there: of each channel and pitch the last note that started before the position, with its velocity, if it hasn't ended, so a pitch that started again sounds as the later note; then the notes that start there. A locate while stopped sends the controller events alone, up to and including those at the cursor (a program change on a part's first tick), so the instrument is ready for live playing. The user settings `midi.chaseNotes`, `midi.chaseControllers`, `midi.chasePrograms` and `midi.chasePitchBend` (all on) choose what is chased; channel and polyphonic pressure and SysEx aren't. Controller events are chased from the whole track, or with `midi.chaseBeyondParts` off only from the MIDI parts under the position; outside parts, then, none. Each controller event in the render snapshot knows its part (`RenderController::part`), so an overlapping part that ended before the position isn't chased. An instrument track chases the controller events of the MIDI tracks routed to it together with its own (`MidiSequence::chase`), so the latest of each kind wins whichever track it is on; those MIDI tracks chase only their notes. The command thread indexes every kind of event, notes by channel and pitch, controller events by kind, of the whole track and of each part (`ChaseTrack`, `makeChaseTrack`), so the audio thread finds each kind's last event by binary search, however long the track. The engine hands the settings to every sequencer (`AudioEngine::setChase`) when it starts and whenever `settings.set` or `settings.reset` changes one; the audio thread reads them as one atomic byte. A chase that doesn't fit into the sequencer's event buffer goes on in the next blocks, each controller event once; the notes are those that sound at the position where they fit. Not chased yet: an instrument that a running track gets anew (a new instrument, a MIDI track routed to another one) waits for the next jump; a new sequencer (a loaded project, a new track, an undo) chases once the cursor moves or playback starts, and editing a controller event before the cursor while stopped doesn't chase again. The index is rebuilt with every graph rebuild; caching it per channel can come when large projects need it.
- Processors that follow the tempo read it from the transport block: the audio engine sets `TransportBlock::tempo` from the project's tempo map, which the render snapshot carries, at each block's position.
