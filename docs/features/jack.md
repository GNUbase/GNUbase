# JACK

The Linux audio backend `jack` (#38), in `src/platform/audio/jack.cpp`, for a running JACK server: jackd2's, or PipeWire's JACK layer (pipewire-jack). It comes after PipeWire in `audio.devices` and before the dummy backend. Like every backend it is reached through `audio.devices`, `audio.setDevice` and `audio.get`, or `--audio jack` in headless mode. JACK MIDI is in [linux-midi.md](linux-midi.md).

- **libjack at run time.** The backend loads `libjack.so.0` with `dlopen` (`src/platform/jacklibrary.h`, shared with JACK MIDI) when it is first used and never unloads it, so GNUbase starts on systems without JACK; `audio.devices` then reports the backend with an error, as it does when no server runs. Only the headers are needed to build (`libjack-jackd2-dev`). GNUbase never starts a server (`JackNoStartServer`). libjack's messages go to the debug log.
- **One device.** `default` is a JACK client named `gnubase` with an input port `in_n` per physical capture port and an output port `out_n` per physical playback port, the server's physical audio ports in its order (`system:capture_1`, ...). Channel names are those ports' names. Under PipeWire, physical ports are those of sound cards; virtual sinks and sources have none. Opening registers the ports and leaves the client inactive; `start()` activates it and connects output *n* to physical playback port *n* and physical capture port *n* to input *n*, trying each connection again for up to half a second, since PipeWire hides the ports of a node for a moment while the graph follows a buffer size request; `stop()` deactivates it, which returns once the server is out of the process callback for good and removes the connections. jackd2 stops the process thread with an asynchronous cancel then, so the callback runs with cancellation disabled: a stop during a late block takes effect after that block, not inside it.
- **Sample rate.** The server has one rate, which is the only one a device lists and opens at; another rate is refused.
- **Block size.** By default a block is the server's buffer. Opening with another block size asks the server for it as its buffer size (`jack_set_buffer_size`), which is every client's, and closing gives the server the size it had back, but only while the server still runs at the size the device asked for: a size another client set since stays (#371). Each cycle is processed in blocks of at most the block size, whatever buffer the server settles on, so any block size up to 8192 works. `audio.devices` lists the powers of two from 32 to 2048 and the current size. PipeWire's JACK layer turns the request into a forced quantum, which it may not follow: by default its client node's `node.force-quantum`, which goes with the client, or with `jack.global-buffer-size` (as for `jack_bufsize`) the graph's `clock.force-quantum`, which would outlast it. Under PipeWire (its libjack says so in `jack_get_version_string`) closing therefore asks for a size of 0, which clears either, instead of forcing the old size (#389).
- **Latency.** Per direction, the largest latency the server reports for the physical ports (`jack_port_get_latency_range`), or a buffer where it reports none. GNUbase's ports are terminal, so it sets no latency of its own in the latency callback.
- **Resets.** JACK's callbacks may come on the process thread (JACK 1 has no other), so they only take notes; a thread of the device's own looks at them every 20 ms (and polls the sample rate and buffer size, since PipeWire calls those callbacks only once the graph runs at the new values) and asks the engine for a reset (`audio.reset`), once a handler takes it and every 20 ms until then (the engine sets its handler only after it has read the device it opened, #371), when the server shuts down, its sample rate changes (the device plays silence until then rather than at the wrong speed), another client changes the buffer size, a physical port goes away, or the latency of the physical ports changes. The device's own buffer size request doesn't reset it: when the server takes it late (PipeWire), the device reads the latency of the physical ports again as its new baseline.
- **Xruns.** The server's xrun callback counts as a device overload, which the performance monitor reports (#45).
- **Block times.** A cycle's first block is stamped with the cycle's start as the server's filtered clock has it (`jack_get_cycle_times`, converted to the host clock through `jack_get_time`; `JackLibrary::cycle`), not with the time the process callback happens to run at (#402); where libjack doesn't tell, the callback's start stands in. Later blocks of the cycle follow at the sample rate.
- **Real time.** The process callback zeroes the output ports and calls the engine's callback in the realtime context; it neither allocates nor locks.
- **Tests.** In `tests/device_tests.cpp`: the device contract suite against jackd and against PipeWire's JACK layer, a running device that leaves itself alone, a buffer size change by another client that resets it (jackd only), a device opened at a block size other than the server's that the server follows and that a later graph change doesn't reset, and under PipeWire (with `jack.global-buffer-size`) no forced quantum left once it closes, a buffer size another client sets while the device is open that stays when it closes (jackd only), a sample rate change that resets the device and silences its callback (PipeWire only, `clock.force-rate`), a reset found before the handler is set that comes once it is, block times within 20 µs of the server's cycle start (jackd only), an xrun from a callback that overruns its cycle, an unplugged sound card, and a project played and recorded over a sound card with loopback cables ([loopback-round-trip.md](loopback-round-trip.md)): the tests register a client with physical ports of their own, as PipeWire's null sinks have none, and remove it. They are skipped where no server runs. The `linux-x64-gcc` CI job starts jackd with its dummy driver (`tools/start-jack.sh`) and sets `GNUBASE_REQUIRE_JACK=1`, and installs pipewire-jack next to PipeWire, whose `GNUBASE_REQUIRE_PIPEWIRE=1` then requires the JACK layer too; the tests fail rather than skip without them.
