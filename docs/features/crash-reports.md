# Crash reports

Every process that opens a `logging::Session` (the app, each plugin host) installs a crash handler (`src/platform/crashhandler.cpp`, #218). On macOS and Linux it writes a backtrace to the log. On Windows it notes the exception in the log and writes a minidump named like the log file, with the extension `.dmp`.

## Windows

- **Out of process (#1883).** The handler starts `gnubase-crashdump` (`src/platform/crashdump.cpp`) from the running program's folder when it is installed, and waits until it watches the process. On a crash the crashed thread notes its thread and exception where the helper reads them and signals it; the helper writes the dump with `MiniDumpWriteDump`, up to three times when a write fails (it fails now and then for another process, for instance while one of its threads starts or ends), and says when it is done. MiniDumpWriteDump suspends every other thread of the process it dumps, so called inside the crashed process it can wait forever for a lock one of them holds, such as the heap's; from another process it needs none. When the handler is installed it waits at most 2 s for the helper to watch the process, well below the time a plugin host has to connect to the engine; a helper that isn't ready by then is ended, and the fallbacks below write the dump. The helper ends when the process ends without a crash, as it waits for the process too, and it is ended when the handler is removed. Like every child process it also belongs to the job that ends GNUbase's children when GNUbase ends (`platform::ChildProcess`). The helper is built for the architecture of the programs next to it: it reads the crashed thread's exception through pointers of the crashed process.
- **Fallbacks.** If the helper can't be started (the program is missing or the system refuses), a thread of the process that waits for a crash from the start writes the dump; without that thread the crashed thread writes it itself. Both can still block on a suspended thread's lock. If the helper is gone when a crash comes, the crashed thread writes the dump itself.
- **Ending the process (#1849).** The crashed thread waits for the dump at most 30 s, then ends the process with `TerminateProcess` and the exit code it would have without the handler: the exception's code, or 3 for `abort()`. TerminateProcess runs no code of the process, unlike returning from the filter or `_exit`, whose DLL clean-up can block on a lock another thread held.
- **Several crashes.** The first crash is the one the dump shows, and the process ends with its exit code. A thread that crashes while another one's crash is handled waits for that to end the process; after 35 s it ends the process itself, with the first crash's code.
- **Removing the handler.** Ending the log session removes the handler. A crash that is being handled by then ends the process, and the session's end waits for it: the events and the helper stay until no crash can use them. A crash whose filter was entered just before the handler was removed ends the process with its code, without a dump.
- **Tests** (`tests/crash_tests.cpp`, through `gnubase-crashtest`): an access violation and `abort()` with and without the helper (a copy of the test program in a folder of its own), the dump's exception code, two threads crashing at once, a crash while another thread holds the heap's lock (without the helper the dump stays empty and the process ends after the 30 s), a crash while the session ends, a filter called after the session ended (no dump), the helper started and ended with the session, and a crash after the helper was killed.
