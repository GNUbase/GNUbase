# Built-in processors and plugins

GNUbase's own processors, which run inside the engine (#114).

- GNUbase's built-in processors (`src/engine/processors`) are `graph::Processor`s that run in the engine: the mixing effects (#114), and test processors: signal generators (sine, noise, impulse), a position probe for transport tests, a note probe that outputs how many notes sound and the sum of their pitches, gain and pan, and a polyphonic test synth, so MIDI-to-audio paths are tested before plugin hosting. Each one handles parameter changes and notes at their sample offset, reports its latency and tail, and forgets its past on `reset`. `processor.list` returns them with their parameters' ids, ranges, defaults, units and, for stepped parameters, the names of their values; `processors::createBuiltin` creates one by id.
- The **mixing effects** are a parametric EQ (six bands, each a cookbook bell or shelf or a Butterworth low or high cut of 6 to 48 dB/oct), a gate, a compressor (soft knee, peak or RMS detection), a look-ahead limiter (1 ms of latency, no sample above its ceiling; sample peaks, not true peaks), a delay (time in ms or a note value at the tempo, feedback, ping-pong, a loop that saturates softly above 0 dB), an algorithmic reverb (Schroeder/Freeverb combs and allpasses with the decay as an RT60 time) and dither (TPDF to 8 to 24 bits, optional noise shaping). Their DSP lives in cores in `src/engine/dsp` that know nothing of graphs or plugins: prepared off the audio thread, then processing in place without allocating or locking, flushing tiny values in their feedback paths so nothing decays through subnormal numbers, and seeding their randomness, so they process the same way on every run (rule 6). They work sample by sample and take parameter changes at their frame, so the block size doesn't change their output either. Parameter changes glide instead of jumping, so automation doesn't click: gains and mixes with a one-pole, EQ frequency, gain and Q by designing the filters anew along the way, delay and reverb lines by changing their length smoothly and reading between samples. Values set before the first block after a reset apply at once. `processors::Effect<Core>` runs a core as a processor, and the channel strip will use the cores directly.
- **Built-in plugins:** `processors::BuiltinFactory` and `BuiltinPlugin` (`builtinplugin.h`) offer every built-in processor through the plugin API ([plugin-api.md](../plugin-api.md)), ids `builtin:<processor id>`: ports, parameters with sample-accurate changes and value names, state, latency and tail. Plugin slots will host them like any other plugin, inside the engine.
