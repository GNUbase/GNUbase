# Loopback round trip

How the tests show that a project plays through each audio backend and that what the backend captures ends up in the recording, where it played (#367). The device contract (`checkDeviceContract`) only plays silence; the round trip sends a signal through.

- **The check.** `checkRoundTrip` in `tests/device_tests.cpp` (declared in `tests/devicecontract.h`, next to the contract) works through the engine API only, as a project would: `audio.setDevice` with the backend, the device and `captureSeconds`, a mono output bus on the loopback's output port, an audio track on it whose audio event plays a burst of noise (0.1 s at 48 kHz) half a second into the project, `audio.start`, `transport.record`, `transport.stop` and `audio.stop`, and then `audio.captureInput` for the loopback's input channel. No track monitors, so nothing feeds back.
- **Where the recording is.** Recorded input goes where the transport played the record offset before it arrived (docs/features/latency-and-monitoring.md). The check looks for the burst up to 8192 frames either way of where it played, by cross-correlation, and checks that it came back: correlation above 0.9, level within 6 dB. It reports how many frames later than where it played the recording lies, which `recordShift` corrects, and fails if that is further from the expected offset than the loopback's tolerance allows. A failure names the backend, the device, the channels and how far off the recording was, with the record offset, the gain and the correlation.
- **The expected offset.** With a cable from an output to an input, the device's latencies cover the round trip, so the recording should lie where it played: 0, give or take a few frames for converters and drivers that report their latency a little wrong. A link inside a sound server's graph is a cycle that the server breaks by delaying it one buffer, whatever latency it reports for the ports at the graph's ends, so there the expected offset is the device's block size minus its record offset.
- **Where it runs.** On every platform against a backend that wraps the dummy device's loopback (the engine takes it for hardware), aligned and with `recordShift`. In the `linux-x64-gcc` CI job against PipeWire, through a null sink of media class `Audio/Duplex` that `tools/start-pipewire.sh` adds (`gnubase-test-loopback`), whose capture ports are the monitor ports of its playback ports; and against JACK, both jackd and PipeWire's JACK layer, through a test client with physical ports whose process callback copies each playback port to the capture port of the same number, a sound card with loopback cables (in the contract's test cases, as its ports come and go).
- **On hardware.** The hidden test `a project plays and records over a hardware loopback` (`gnubase-tests "[hardware]"`) runs the check on the loopback named by `GNUBASE_LOOPBACK=<backend>,<device id>,<output>,<input>`: channels from 0, an empty id for the backend's default device, and the id may hold commas. `GNUBASE_LOOPBACK_TOLERANCE` sets the tolerance in frames (default 64). It is for a maintainer's machine with a loopback cable or a virtual loopback device, run once per backend: `asio`, `wasapi`, `wasapi-exclusive`, `coreaudio`. Without the variable it is skipped.
