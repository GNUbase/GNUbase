# Audio device loss and sample rates

What the audio engine does when its device goes away and comes back, and when the project and the device run at different sample rates (#46).

- **Device loss.** Every backend asks for a reset (`Device::requestReset`) when its device goes away: a removed WASAPI endpoint, a CoreAudio device that dies, a PipeWire node or JACK server that goes away, an ASIO driver's reset request. The engine posts `audio.reset`, which opens the device again with its settings. If that fails, the device is **lost**: the engine closes it and goes on without one. The transport, the project and every command keep working; the transport keeps its play state but stops moving, since only the audio thread moves it. `audio.get` reports `lost` with the backend, the device id, the reason it can't be opened and whether it ran (`restart`), and `audio.changed` announces the loss.
- **Reconnecting.** While a device is lost, a thread of the audio engine posts `audio.reset` every 500 ms. The first one that opens the device ends the loss: the device opens with its settings, the graph is compiled for it and it starts again if it ran, so playback goes on from where it stopped, without a restart of GNUbase. Tries that fail again change nothing and announce nothing. `audio.setDevice` ends the wait, also when it fails, except for a dummy device that is still unplugged. The backends have no common notification for returning devices, so all are polled alike.
- **Simulated loss.** `audio.simulateDeviceLoss` with `connected: false` unplugs the dummy device: its driver asks for a reset, which fails while it is unplugged, and so does `audio.setDevice` with the dummy device. With `connected: true` it is plugged in again, and the next try opens it. Tests use it, and the fake backend in `tests/audio_tests.cpp` covers the same for a backend's device.
- **Sample rate mismatch** (reference manual pp. 26, 129): the device runs at the project's sample rate where it can. A device opened without a `sampleRate` opens at the project's if its `sampleRates` list it, otherwise at the driver's current rate; an explicit `sampleRate` wins. When the project's sample rate changes (`project.set`, `project.load`, `project.new`), a device that supports the new one is opened again at it and keeps running, and `audio.changed` announces it. Otherwise the mismatch stays: `audio.get` has the project's rate as `projectSampleRate` and `sampleRateMismatch: true`, for the status line to show, and the device plays the project faster or slower, as positions are in the project's samples and one device frame plays one of them.
