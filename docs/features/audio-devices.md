# Audio devices: startup, loss and sample rates

Which audio device the app opens and starts (#712), what the audio engine does when its device goes away and comes back, and when the project and the device run at different sample rates (#46).

## The device at startup (#712)

As in the reference (manual pp. 21–22), the driver selected in Studio Setup is the one the program uses from then on, also after a restart, and it runs as soon as the program does: Play moves the cursor, the metronome sounds and recording works right after launch.

- **Starting.** The windowed app (`app::setUpWindowedEngine`) opens its device with `audio.setDevice` with `start` and `fallBackToDummy`, so the device runs before the main window shows, and only then loads the project given on the command line.
- **Which device.** `--audio BACKEND` wins, with that backend's default device. Otherwise the app opens the user settings `audio.backend` and `audio.device`: the device the user chose last. With neither, `audio.backend` is empty, which `audio.setDevice` takes as the platform's default backend (`audio::defaultBackend()`): WASAPI (shared) on Windows, CoreAudio on macOS, PipeWire on Linux, with its default device, the one the OS plays everything else on. It isn't the preferred backend that `audio.devices` lists first, ASIO on Windows, whose default device is merely the first driver installed. An engine without the platform's default backend, as in tests with fake backends, takes the preferred one. `--sample-rate` and `--block-size` apply to whichever device opens; without them the device runs at the project's rate if it can and at the driver's block size.
- **Remembering the choice.** `audio.setDevice` with `remember` saves `backend` and `device` as given into `audio.backend` and `audio.device`, in one write of `settings.json` (`settings::Store::set` with several values), and sends `settings.changed`. Studio Setup switches drivers like that. It saves only once the device runs as asked: a device that fails, or the dummy device that plays instead, leaves the user's choice as it was, so the next start tries the chosen device again. Other `audio.setDevice` calls, such as a test's or a script's, and `--audio` save nothing. If the settings file can't be written (another GNUbase holds its lock too long), the command fails with the new device open and running, which `audio.changed` announces.
- **When it can't be used.** A device that can't be opened or started, or a backend this build doesn't have (settings copied from another OS), doesn't stop the app: `fallBackToDummy` opens the dummy device instead, without capture memory and at the sample rate and block size asked for, and starts it, logs a warning, and the app prints it on stderr. `audio.get` has the failure as `failed` (backend, device id, reason) until another device replaces that dummy device, and Studio Setup shows it in its message line when it opens. Picking a driver there that opens ends it. Only if not even the dummy device opens does the app exit with code 3. This differs from a device lost while it ran (below): the engine doesn't keep trying the unavailable device, since it may never return (a device of another computer); the user picks one in Studio Setup.
- **Switching keeps it running.** `audio.setDevice` starts the new device if the one it replaces ran, or was lost and meant to start again (`lost.restart`), so a driver picked in Studio Setup plays on at once; `start` says otherwise. A switch that fails, leaving no device or one that does not run, passes this on: the next `audio.setDevice` starts its device, so picking a driver that fails and then one that works doesn't leave the app stopped, unless `audio.stop` or `audio.start` decided anew. A device that opens but fails to start stays open and stopped, and the command fails. `audio.render` still needs a stopped dummy device: `audio.stop` first, or `start: false`.
- **Headless and tests.** Headless runs (`app::setUpEngine`) open `--audio`'s backend or the dummy device and leave it stopped, whatever the user settings say, as before: MCP clients and scripts start it with `audio.start`, and offline rendering with `audio.render` stays deterministic. The UI tests' `test::UiApp` sets up the engine the same way.
- **Tests:** `tests/app_tests.cpp` starts the windowed app's engine with a fake backend and a settings folder: the device runs and the transport moves after `transport.play`; the device chosen with `remember` opens on the next start; a saved device that doesn't open, and a saved backend this build lacks, start on the dummy device with `failed`, keeping the user's choice; `--audio`, `--sample-rate` and `--block-size` win; headless set-up stays on the stopped dummy device. `tests/audio_tests.cpp` covers `start`, keeping a running or lost device running, the fallback for open and start failures, the platform's default backend and `remember`, and `tests/settings_tests.cpp` writing several settings at once. `tests/studiosetup_tests.cpp` checks that Apply on another driver remembers it and keeps it running, and that the dialog shows `failed`.

## Device loss and sample rates

- **Device loss.** Every backend asks for a reset (`Device::requestReset`) when its device goes away: a removed WASAPI endpoint, a CoreAudio device that dies, a PipeWire node or JACK server that goes away, an ASIO driver's reset request. The engine posts `audio.reset`, which opens the device again with its settings. If that fails, the device is **lost**: the engine closes it and goes on without one. The transport, the project and every command keep working; the transport keeps its play state but stops moving, since only the audio thread moves it. `audio.get` reports `lost` with the backend, the device id, its name as it was while it was open (#455; the id if it had none), the reason it can't be opened and whether it ran (`restart`), and `audio.changed` announces the loss.
- **Reconnecting.** While a device is lost, a thread of the audio engine posts `audio.reconnect` every 500 ms, one at a time: it posts the next try only once the last one ran, so tries don't queue up behind a long command and reset a device that is already back (#406). `audio.reconnect` does nothing unless a device is lost. The first try that opens the device ends the loss: the device opens with its settings, the graph is compiled for it and it starts again if it ran, so playback goes on from where it stopped, without a restart of GNUbase. Tries that fail again change nothing, announce nothing and stay out of `engine.commandLog` (`CommandContext::leaveOutOfLog`), which would otherwise fill with them in about two minutes; the try that opens the device is logged. `audio.setDevice` ends the wait, also when it fails, except for a dummy device that is still unplugged. The backends have no common notification for returning devices, so all are polled alike.
- **Failing over** (#404). The reference manual describes no failover, so this is GNUbase's own and off by default: the user setting `audio.fallbackDevice` is `none`. With `dummy`, the engine opens the dummy device with its defaults (without capture memory) when a device is lost, and starts it if the lost device ran, so the transport moves and the project plays on, though nothing can be heard. With `default`, it opens the lost device's backend's default device, which the system usually moves to another device when one is unplugged, and the dummy device if that doesn't open. `audio.get` then reports the fallback as `device` and the chosen device as `lost`. While the fallback plays, `audio.reconnect` tries the lost device only once its backend lists it as available again (the dummy device: once it is plugged in), as every try closes the fallback first: drivers often allow one open device at a time. A backend whose list doesn't say whether a device is there (`Backend::listsPresence`) is the exception: ASIO lists a driver as unavailable from the open that failed until one succeeds, as only opening it tells whether its hardware is back, so while it is listed like that, `audio.reconnect` tries it every 3 seconds instead of never. When it opens, it opens with its settings and runs if the fallback ran, and the fallback is closed. `audio.start` and `audio.stop` act on the fallback and decide whether the device returns running; `audio.set` fails, as it would change the fallback's settings while the user means the device's; `audio.setDevice` ends the loss as always. The fallback dummy device can't be unplugged with `audio.simulateDeviceLoss`, so tests lose the dummy device and fail over to it; while it plays for another backend's lost device, `connected: false` fails and changes nothing, as the dummy device would otherwise stay unplugged once that device returned. A change of the setting applies with the next try to open the lost device, if no fallback plays yet. A try that fails while the fallback plays interrupts it, and it starts over: every 3 seconds for an ASIO driver whose hardware is still gone, and with every try for a device that a backend lists as available although it can't be opened.
- **Starting and stopping while lost** (#410). `audio.stop` clears `lost.restart` and `audio.start` sets it, each announced with `audio.changed`, so the device returns stopped or running as the client last asked.
- **Failed commands that closed the device** (#395). `audio.setDevice` closes the old device before it opens the new one, and `audio.set` opens the device again with its old settings when the new ones fail, or leaves no device when those fail too; `audio.reset` may fail to start the device it opened again. A failed command's events go nowhere, so in these cases the engine broadcasts `audio.changed` with the status the device is left in before the command fails, and clients don't keep showing a device that changed or is gone.
- **Simulated loss.** `audio.simulateDeviceLoss` with `connected: false` unplugs the dummy device: its driver asks for a reset, which fails while it is unplugged, and so does `audio.setDevice` with the dummy device. With `connected: true` it is plugged in again, and the next try opens it. Tests use it, and the fake backend in `tests/audio_tests.cpp` covers the same for a backend's device.
- **Sample rate mismatch** (reference manual pp. 26, 129): the device runs at the project's sample rate where it can. A device opened without a `sampleRate` opens at the project's if its `sampleRates` list it, otherwise at the driver's current rate; an explicit `sampleRate` wins. When the project's sample rate changes (`project.set`, `project.load`, `project.new`), a device that supports the new one is opened again at it and keeps running. Otherwise the mismatch stays: the device's entry in `audio.get` has the project's rate as `projectSampleRate` and `sampleRateMismatch: true`, for the status line to show ([status-line.md](status-line.md)), and the device plays the project faster or slower, as positions are in the project's samples and one device frame plays one of them. Either way `audio.changed` announces the new rate, which `audio.get` also has at its top level as `projectSampleRate`, with or without a device.
