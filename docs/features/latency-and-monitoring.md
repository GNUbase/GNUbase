# Latency compensation and monitoring

How recorded input lines up with what played, and how input is heard while it is played (#44, #100, reference manual pp. 340–341, the device settings on pp. 19–20 and the automatic monitoring preference on p. 1623). Recording onto tracks comes with #96 and builds on what is here.

- **Device latency.** Every device reports its input and output latency in frames as its driver tells them (`Device::latency`): ASIO asks the driver after creating its buffers, WASAPI adds its buffers to the stream latency. `audio.get` shows them. A driver that says its latencies changed (ASIO's `kAsioLatenciesChanged`) asks for a reset, which opens it again and reads them anew.
- **Record offset.** The performer hears playback the output latency late, and what they play reaches GNUbase the input latency after that; a cable from an output to an input does the same. So the input that arrives at a device frame belongs with the audio that went out `inputLatency + outputLatency` frames before. Drivers don't always count their converters, so `recordShift` in `audio.setDevice` moves recordings that many frames later (negative: earlier), as the reference's record shift does. `recordOffset` in `audio.get` is the result, `inputLatency + outputLatency - recordShift`, at least 0.
- **Where input goes.** The audio thread keeps where the transport played each of the device's last frames, as many as the record offset plus a block (`PlayedPositions` in `src/engine/audio/transport.h`). An input frame goes where the frame the record offset before it played, not to the cursor minus the offset: input that comes back after a cycle jump, a locate or a stop still lands where it played, and so does the last offset's worth of input after playback stops. Frames that played while the transport stood are not recorded. Plugin latency on the recording's path is #71's ("Adjust for Record Latency").
- **The dummy device** reports latencies that `audio.setDevice` gives it (`inputLatency`, `outputLatency`). With `loopback` its inputs carry its outputs back, the round trip later, as a cable from each output to the input of the same number would; the round trip has to be at least a block, since the outputs of the block being processed aren't there yet. `audio.captureInput` reads what an input channel recorded at each project position, by the rules above, for the dummy device's capture length from position 0; a later cycle lap overwrites the one before. It is the loopback test of the acceptance: a ramp played at a position is recorded at that very position, sample for sample (`tests/latency_tests.cpp`).
- **Monitoring through the graph.** An audio track that monitors hears its input bus: the bus's node feeds the track's channel, which plays the input with its events through the fader, panner and output routing like anything else, in the same block it arrived in. The monitored signal is late by the device's input and output latency and nothing more (the reference: "The monitored signal will be delayed according to the latency value"). #96 records from the input bus, not from the channel, so monitoring never changes what is recorded.
- **When a track monitors.** Audio tracks have two buttons, `monitor` and `recordEnable` (`channel.set`; saved with the project in `gnubase.json`, since DAWproject has neither). The monitor button always monitors, in every mode: that is manual monitoring. A record-enabled track monitors as the user setting `audio.autoMonitoring` says, the reference's Auto Monitoring preference: `manual` never, `whileRecordEnabled` always, `whileRecording` only while the transport records, and `tapeMachine` (the default) while it stands or records but not while it only plays back, so a take sounds as recorded when it is played back. For external monitoring through a mixer, the reference's advice applies: `manual`, with every monitor button off. `transport.record` starts recording (starting playback if it stood) or punches in while it plays, `transport.record` with `record: false` punches out, and `transport.stop` ends both; `transport.get` reports `recording`.
- **Switching.** The audio thread decides per block, from the transport block's `playing` and `recording`, so monitoring follows the transport at the block where a start, stop or punch takes effect (`Monitoring` in `src/engine/audio/automation.h`). The track's channel strip passes the input on to the track player only while the track monitors; it glides in or out linearly over the block in which that changes, so switching doesn't click. A new track starts at its state without a glide. A new mode applies at once: the engine reads the setting after every command and builds a new graph when it changed.
- **Direct monitoring.** Drivers that can route an input to an output themselves (`DeviceInfo::canMonitorDirectly`: ASIO's input monitor, which the driver may support or not) monitor without the round trip through the engine. `canMonitorDirectly` in `audio.devices` and `audio.get` says which can, and `directMonitoring` in `audio.setDevice` turns it on (the reference's checkbox in the device's settings); a driver that can't refuses, and no device is open then. With it, an audio track that plays into an output bus doesn't get its input through the graph: while it monitors, by the same rules as above, its input bus's ports play on its output bus's ports in the device (`Device::monitorInput`), at the fader's level, and a mono input on a wider bus at the track's pan between the bus's first port and the one after it, as ASIO pairs them. Other inputs play on the port of the same channel. Automation doesn't reach the hardware. Each input port plays on one output, so the first monitoring track in track order that uses it wins. Tracks that play into a group are monitored through the graph, since the group isn't on the device. The engine sets the routes again whenever the project or the mode changes and after every transport command, as the transport is requested (the device switches at once, not at the audio thread's next block), and turns them off when it closes the device. The dummy device monitors directly by adding the inputs to what it outputs and captures, splitting a pan linearly.
