# CoreAudio backend

The audio backend on macOS (#36): `coreaudio` in `audio.devices` and `audio.setDevice`, the preferred backend there. The code is `src/platform/audio/coreaudio.cpp`; the device interface it implements is in [architecture.md](../architecture.md) (Audio devices).

- **Devices.** Every HAL device that has channels and isn't hidden, aggregate devices included: macOS combines several devices into one in Audio MIDI Setup, on one clock with drift correction, and that is how GNUbase uses separate input and output devices (such as a Mac's built-in microphone and speakers, which are two devices). A device's id is its UID, which stays the same across runs; an empty id opens the default output device, or the default input device if there is no output. Channel names are the driver's element names, or "Input n" and "Output n" where it has none. There are no clock sources and no control panel yet.
- **Sample rate.** The rates a device lists one by one, the usual rates (44.1 to 192 kHz) within the ranges it lists, and its current rate. Opening at another rate changes the device's nominal rate and waits until it runs at it (at most 3 s); closing sets the rate it had before, so other programs find the device as they left it.
- **Block size.** The HAL calls GNUbase once per I/O cycle; each cycle is processed in blocks of at most the block size, so any block size up to 8192 works. Opening sets the process's I/O buffer size to the block size, as far as the device's range allows; by default a block is an I/O cycle at the device's current buffer size. `audio.devices` lists the powers of two from 32 to 2048 within the device's range and its current size.
- **Samples.** The HAL hands over interleaved 32-bit floats per stream and converts to and from the hardware's format itself; GNUbase spreads the streams' channels over its inputs and outputs in order.
- **Latency.** Per direction, the device's latency, its safety offset and its first stream's latency, plus the buffer size.
- **Resets.** The device asks for a reset (`audio.reset`) when it goes away, its channels change or another program changes its sample rate. Notifications come on a dispatch queue of the device's own, which is drained before the device goes.
- **Audio workgroup.** CoreAudio's I/O thread belongs to the device's audio workgroup (macOS 11), which tells the scheduler which threads work towards its deadline. `Device::workgroup` hands it out, and the engine's processing threads (`rt::WorkerPool`) join it as they start, after taking their time-constraint priority, and leave it as they end; the engine starts them after opening the device and stops them before closing it.
- **Real time.** The I/O callback neither allocates nor locks. `stop` clears the callback and waits until a cycle that still has it has returned, so no block comes after it.

**Tests.** `the CoreAudio backend lists its devices and refuses unknown ones` runs with the unit tests on macOS. The hidden hardware tests (`gnubase-tests "[hardware]"`) open every device: `every hardware backend keeps the device contract` (section `coreaudio`) and `worker threads join the audio workgroup of a CoreAudio device`.
