# Real-time priority on Linux

How the engine's worker threads (`rt::WorkerPool`, [architecture](../architecture.md)) get real-time priority on Linux, where a stock desktop user may not take it (#364).

- **Directly where the user may.** A worker first sets SCHED_FIFO itself, which needs `RLIMIT_RTPRIO` (the `audio` group's limits on many distributions) or `CAP_SYS_NICE`. Once a real-time audio thread runs jobs, the workers move to one priority below it (`workerPriority`).
- **Otherwise through rtkit.** When that is refused, the worker asks rtkit (`org.freedesktop.RealtimeKit1`, which desktops run to hand out real-time priority) over the system bus, with libdbus: it reads rtkit's `MaxRealtimePriority` and `RTTimeUSecMax`, lowers the process's `RLIMIT_RTTIME` to that maximum if it is higher (rtkit serves only processes with such a limit; PipeWire's real-time module sets the same one), and asks `MakeThreadRealtime` for its own kernel thread id at one below `MaxRealtimePriority`, where rtkit puts audio threads that ask it for more, such as PipeWire's data thread. rtkit's threads have SCHED_RR with `SCHED_RESET_ON_FORK`, which the worker keeps, and without `RLIMIT_RTPRIO` a thread may only lower its priority: following its caller, a worker goes down to one below the audio thread if that is lower, and stays there. `DBUS_SYSTEM_BUS_ADDRESS` overrides where the system bus is, as for libdbus itself; each worker opens a private connection, asks, and closes it, all before the pool's constructor returns. Each request waits at most 3 s for rtkit, which the bus may have to start first.
- **Neither.** Without a system bus, without rtkit, or if rtkit refuses, the worker runs at normal priority, so it doesn't help the audio thread and `audio.get` reports `limitedBy: "realtime"` in `processing`. Workers that got real-time priority either way count alike: `activeThreads` includes them.
- **Sleeping now and then.** `RLIMIT_RTTIME` kills a real-time thread that runs longer than its limit (rtkit's default is 200 ms) without sleeping. A worker that spins from one job to the next would never sleep, so a worker that took part in a job sleeps for 50 us when it hasn't for 50 ms. It misses a little of a job then, which the others and the audio thread do.
- **Tests.** `WorkerPoolFaults::refuseDirectRealtime` makes the direct request fail. `tests/testutils/fakertkit.h` is a fake rtkit on a D-Bus server of its own, which it makes the system bus through `DBUS_SYSTEM_BUS_ADDRESS`: it grants or refuses requests and records them, or plays a bus without rtkit or no bus at all. The worker pool tests check the requests (one per worker, its own thread id, the priority) and `RLIMIT_RTTIME`; the multi-processing tests check `processing` in `audio.setProcessing` and `audio.get`. A test counts a busy worker's voluntary context switches to check that it sleeps.
