# Self-contained projects and backups

A project that is moved or archived needs its media with it (#170). `src/engine/media/backup.h` has the file work; the commands are in the project model.

- The **project folder** is the folder of the file the project was last saved as or loaded from (`project.location`; `project.save` announces it with `project.saved`); its **media folder** is `Audio` in it. A project without a file has neither. Auto saves go into its `Auto Saves` folder ([project-files.md](project-files.md)).
- `media.add` with `copy` adds a file from outside the project folder where it is and copies it into the media folder as a job, which then points the media file at the copy (the engine part of the import option, #92). Names stay unique: `take.wav`, `take-2.wav`.
- `media.prepareArchive` copies every media file from outside the project folder into the media folder as a job, then points the media at the copies as one undo step; missing files are listed and left alone. Saved without embedding, the project then refers to its media relative to itself, and the folder can move.
- `media.relink` points media files at other files with the same sample rate and channel count, as one undo step. The copy jobs give it `project`, the project open when they started, so that one opened meanwhile is left alone: its entries are skipped, the copies removed and the media reported as `changed` ([pool.md](pool.md)). An entry with `length` is skipped, not refused, if its file went or doesn't fit, as `media.locate`'s job needs.
- `project.backup` writes a copy of the project as it is into an empty or new folder: `<name>.dawproject`, its media in `Audio` and its frozen tracks' freeze files in `Freeze` (each once, also when several tracks play it; [render-in-place.md](render-in-place.md)), referred to relatively, so the backup opens on another machine. The open project and its files stay as they are. It runs as a job (see [architecture.md](../architecture.md#engine-api)): it copies in 1 MB chunks, reports progress, and if it is cancelled or fails it removes what it wrote. The files it reads are opened as the readers open files, so a file can be replaced or deleted while the backup reads it, on Windows too, and the copy reads the old file to its end (#963). Options:
  - `minimize` writes only the ranges of each audio file that its audio events play, plus `handles` seconds on each side, merged where they overlap and joined one after the other; the events' offsets move with them. Ranges of a file at another sample rate than the project's start on the resampling grid, which counts from the file's first frame (a multiple of 147 frames for 44.1 kHz in a 48 kHz project), so every file plays sample for sample the same. A minimized file keeps its format where GNUbase writes it without changing a sample (16- and 24-bit WAV, AIFF and FLAC, float WAV) and is a 32-bit float WAV otherwise, which holds every sample as it is read. 32-bit integer and 64-bit float files, whose samples don't fit into a 32-bit float, and Broadcast Wave files, whose time reference counts from the first frame, are copied whole, as is a file that no range leaves out. Other metadata, such as tags or cue points, isn't kept in minimized files.
  - `removeUnused` leaves out clips that no audio event uses and media that no clip uses.
  - `name` names the file and the backed-up project; without it, the backup gets the name that `project.location` tells as `name`. It must be a name that files can have on every platform: no `<>:"/\|?*` or control characters, no dot or space at the end, which Windows drops, and not a name that Windows keeps for a device (`CON`, `PRN`, `AUX`, `NUL`, `COM0` to `COM9`, `LPT0` to `LPT9`, also with a superscript 1 to 3), or such a name with an extension (`nul.mix`), which is a device there before Windows 11. Without `name` the backup is named after the project file: its whole name without the dots and spaces at its end and the `.dawproject` extension before them, as for versions and auto saves ([project-files.md](project-files.md)), or else after the project. Either name then has the characters files can't have replaced by `_`, the dots and spaces at its end dropped and `_` before a device's name: a project `CON`, or a file `CON.dawproject` on Linux, backs up as `_CON.dawproject`.
  - `activate` opens the backup once it's done, unless the project changed meanwhile; the result says whether it was opened, and why not.
  - The files in the project folder's `Mixdown` folder, where File > Export > Audio Mixdown suggests to put mixdowns ([mixdown.md](mixdown.md)), go along into the backup's `Mixdown` folder, with the folders in it, empty ones too, unless `skipMixdown` is true (the reference manual, p. 137). A backup into a folder inside `Mixdown` leaves itself out. Links to folders in there aren't followed, so one to a folder above it doesn't copy that folder again and again. Files and folders get free names as media do: two files whose names differ only in case, from a file system that tells them apart, become `Mix.wav` and `mix-2.wav`, so that neither overwrites the other on a backup drive that doesn't, and a file `Notes` and a folder `notes` become `Notes` and `notes-2`, which can both be there.
  - `currentVersionsOnly` (offline processing #141, track versions #165) and `skipVideo` (#198) are accepted and do nothing until those exist.
  - A media or freeze file that can't be read doesn't stop the backup: the result lists it under `missing` (`{media, path}`, or `{track, path}` for each track that plays a freeze file), and the backup keeps its old path. Nor does a file in the `Mixdown` folder that can't be read, such as one that another program locks or that went meanwhile, or a folder in there that can't be listed: they are listed as `{path}`, a folder as `{path, folder: true}`, and left out, the folder with what it holds (and without the folders in it that it couldn't list either).

- `project.location`'s `name` is the name a backup gets without `name`: after the project file, or else the project, made a name that files can have, as above.

## In the UI

- **File > Back up Project...** (`file.backup`, `ui::ProjectFiles`) asks for the folder in the OS's folder dialog, then shows the Back up Project Options dialog (`resources/ui/backup-project.rml`, the reference manual pp. 136-137): Project Name, which starts as the engine's default name (`project.location`'s `name`, also for a project without a file) and goes to the engine as `name` only when it was changed, so the engine's own default name stays as it is otherwise; Keep Current Project Active, checked by default, which is `activate` unchecked; Minimize Audio Files (`minimize`), Make Offline Processing Permanent (`currentVersionsOnly`), Remove Unused Files (`removeUnused`), Do Not Back up Video (`skipVideo`) and Do Not Back up Mixdown Folder (`skipMixdown`). Make Offline Processing Permanent and Do Not Back up Video are disabled until they have an effect (#141, #165, #198). OK sends `project.backup`.
- While the backup's job runs, `resources/ui/backup-progress.rml` shows its progress and the file it copies (`job.progress`); its Cancel, or closing it otherwise, also with its window, such as a panel's own window that the user closes, cancels the job, which then removes what it wrote (#1206). Once the job ended the dialog closes. It doesn't take its turn with the other project dialogs, which open over it meanwhile, such as an error or another backup's options, and quitting doesn't close it before it asks about unsaved changes: the backup runs on unless GNUbase quits, which cancels it. Each window shows one backup's progress at a time: a backup asked for in another window meanwhile, such as a panel's own window, shows its progress there (#1109), and one asked for in a window that shows another's progress runs without. What a backup has to say once it ended shows in its window, or in the main window if that window went meanwhile (#1206). A backup that is refused, or whose job fails, shows its error, as does one that couldn't read files or Mixdown folders (`missing`, counted by path, as files and folders, and shown by name) or was to be opened but wasn't (the job result's `activationError`).
- The UI keeps the job ids that its own `project.backup`s returned and reports only those jobs, in the window that asked: a backup that an MCP client or a Lua script starts shows nothing there (#944).
- **Media > Prepare Archive** (`pool.prepareArchive`, `ui::PoolPanel::prepareArchive`) first asks, as the reference does (p. 135), when the project has files outside its folder that it can copy (`pool.get`'s `externalFiles` without its `missingExternalFiles`): `resources/ui/prepare-archive.rml` says how many, and how many more are missing, before it asks whether to copy them, and sends `media.prepareArchive` with Proceed. Without such files, or for a project without a file, which the engine refuses, it sends it at once. Its result shows in the pool's message line, as the other Media menu commands' do ([pool.md](pool.md)): its progress, then e.g. "Copied 2 files into the project folder; 1 missing file wasn't copied; 1 file changed meanwhile and was left as it is.", or why it failed, such as a project that was never saved.

## Tests

`tests/backup_tests.cpp` tests the commands, `tests/projectfiles_tests.cpp` the dialogs. What must happen while a backup or copy job runs, such as `job.cancel`, an edit that keeps `activate` from opening the backup, a relink by hand, or another backup into the folder the job writes into, happens while `test::HeldJob` (`tests/testutils/heldjob.h`) holds the job at its first `job.progress`, mostly through `test::whileHeld`, so that the job can't get further or end first, however the threads are scheduled (#1154). It can hold the first jobs of a kind too, each at its first `job.progress`, as for two backups whose progress shows in two windows at once; `a HeldJob holds the first jobs of a kind, each once, and lets the later ones run` tests that. Only the job's thread waits: events and commands go on meanwhile, as `a job held at its first progress keeps no command or event waiting` shows; another test has a hold lapse and the job run free, held at its first `job.progress` only, and `whileHeld fails a test whose hold lapsed`, tagged `[!shouldfail]`, shows that `whileHeld` fails a test whose hold lapsed while it did what must come first, also while the job still runs: there the test keeps the job at its next `job.progress` with a hook of its own, so that only the lapse check fails (#1430). `a file being backed up can be replaced and deleted meanwhile, on Windows too` doesn't hold a job at its first progress: `Engine::setJobProgressHook` runs on the job's thread after each chunk's progress, and there the test replaces or deletes the file being read, so the copy really has it open (#963).
