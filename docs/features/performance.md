# Performance data and benchmarks

Measuring the engine's load while it plays, and benchmarks (#24).

- **Performance data** (#24): the audio engine times every block (`PerformanceMeter`). The load is the share of the block's duration spent processing it, averaged over about 0.3 s, with the peak block and the overloads (blocks above 1) since the last reset, and each processing thread's load from the time it spent on nodes. The audio thread publishes them through a triple buffer; `audio.performance` returns them with the disk streams' load (how far the stream furthest behind has run empty) and the playback dropouts. `audio.resetPerformance` starts a new measurement, like clicking the overload indicator in the performance monitor (#45), and tells every client with an event; a new device or new processing threads start over from nothing. A disk stream's load counts the blocks it still has to fill, so a new stream and one just located read as empty.
- **Performance monitor data** (#45, reference manual pp. 1589–1590): `audio.performance` has what the performance monitor shows. Real time is `load`, the peak is `peak`, the disk cache is `diskLoad` with `diskDropouts` for its overload indicator, and `blockSize` is the device's current block size (0 without a device). The processing overload counter `overloads` counts the blocks over their time plus `deviceOverloads`, the dropouts the driver reported: `Device::overloads()` counts the calls a backend makes to `reportOverload()`, from any thread, real-time safe. A block that ran late and that the driver also dropped counts twice. The dummy device reports one for every `audio.simulateOverload`. The anticipative load (the manual's preprocessed load) waits for anticipative processing, and the dropout list with positions and related tracks for a later ticket.
- **Driver dropouts and restarts** (#354, reference manual p. 1589): every backend reports its driver's dropouts to `reportOverload()`. ASIO: the driver's `kAsioOverload` message. WASAPI: a capture packet flagged as a data discontinuity, except the first after starting, which drivers may flag for the start. CoreAudio: the device's processor overload notification. JACK: the server's xrun callback. PipeWire: every increase of the xrun duration the graph's driver adds up in its clock (`spa_io_clock::xrun`, which ALSA's drivers keep; `XrunCounter`), ignoring the first cycle after starting and a switch to another driver's clock. The engine's own late blocks already count as blocks over their time. An `audio.reset`, which drivers ask for when their settings change or they lose sync, keeps the measurement (peak, overloads, cycles and the device dropouts so far); a reset that loses the device ends it. The manual counts a restart "due to the internal detection of excessive processing delay" as a dropout, not one after a settings change (#418), so the restart itself doesn't count: a backend whose driver asks for a reset because of a dropout reports that dropout with `reportOverload()` first. ASIO: a resync request; WASAPI: an endpoint that stops responding (the hang timeout) or fails. Resets for a new buffer size, latency or sample rate (ASIO's other reset messages, CoreAudio's rate change, the device following the project's sample rate) count nothing. `audio.resetPerformance` reads the device's count once, so a dropout reported meanwhile is in either the measurement that ends or the new one.
- `gnubase-bench` (`tests/bench`) measures the engine by rendering instrument tracks offline: `workers` with 1, 2, 4 ... threads up to the hardware's, `tracks` with 8 to 128 tracks and `blockSizes` with blocks of 32 to 2048 frames. CI runs it with `--quick` after the tests of every platform's Release build, without failing on its numbers, and keeps the JSON results as artifacts.
